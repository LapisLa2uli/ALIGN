# Coding Agent Prompt: Music Performance Error-Annotation Pipeline

Copy everything below into your coding agent (Claude Code, Cursor, Codex, etc.) as the task specification.

---

## Objective

Build a desktop/local web application that lets a user turn a music score (MusicXML or PDF) plus a recording of themselves performing it into a labeled training-data sample for a performance-error-detection model. Human labeling should be assisted by an automatic alignment step so annotators are confirming/correcting candidate errors rather than finding every error from scratch. The final output per sample is a data bundle containing:

1. A schema-versioned JSON file of labeled errors/repetitions/non-errors, with timestamps (relative to the *performer's* audio), numeric deviation values, and severity
2. A log-mel spectrogram of the real performance audio
3. A log-mel spectrogram of a MuseScore-synthesized "reference" rendering of the score
4. The clean, human-verified MusicXML used to generate the reference
5. (Optionally, in synthetic mode) additional perfectly-labeled samples generated by programmatically corrupting the score and re-rendering it

## High-Level Pipeline

```
[Score Input: .musicxml OR .pdf]
        │
        ├── if .pdf ──► Audiveris OMR ──► draft MusicXML ──► Manual Correction UI ──► verified .musicxml
        │
        └── if .musicxml ──► used directly as verified .musicxml
                                          │
                     ┌────────────────────┴─────────────────────┐
                     │                                           │
        [User uploads/records performance audio]      [MuseScore CLI renders verified .musicxml → reference audio]
                     │                                           │
                     │                                [Log-mel + chroma/CQT features of reference audio]
                     │                                           │
                     └───────────────────┬───────────────────────┘
                                          │
                     [Chroma/CQT DTW alignment: performance vs. reference audio]
                                          │
                     [Auto-flagged candidate error regions + numeric residuals
                      (cents-off-pitch, ms-off-beat)]
                                          │
        [Annotation UI: NLE-style zoomable timeline (DaVinci Resolve-like) + score view,
         drag-select ranges, pre-highlighted candidates, confirm / correct / reclassify,
         label new regions, mark non-errors, optional performer self-marks,
         optional inter-annotator review]
                     │
        [labels.json: error / repetition / non-error ranges, severity, numeric deviation]
                     │
        [Log-mel spectrogram of performance audio]
                     │
                     └──────────────► [Final bundle: labels.json + performance_mel.npy +
                                        reference_mel.npy + verified_score.musicxml + metadata.json]

[Parallel batch mode] verified .musicxml ──► Synthetic Error Injection ──► corrupted MusicXML
                                          ──► MuseScore render ──► perfectly-labeled synthetic sample
                                              (same output bundle shape, auto-generated labels.json)
```

## Detailed Requirements by Stage

### Stage 1 — Score Ingestion

- Accept `.musicxml`, `.mxl` (compressed MusicXML), or `.pdf` as input.
- If MusicXML/MXL: validate it parses correctly (use `music21` in Python) and pass through to Stage 3.
- If PDF: send to Stage 2 (OMR).
- Reject/flag corrupt or unparseable files with a clear error message rather than failing silently.

### Stage 2 — OMR via Audiveris + Manual Correction

- Invoke Audiveris in batch/headless mode via subprocess:
  ```
  Audiveris -batch -export -output <output_dir> <input.pdf>
  ```
- Capture Audiveris logs/stderr and surface any warnings (e.g., low-confidence pages) to the user.
- After Audiveris produces a draft `.mxl`/`.musicxml`, open it in an embeddable score-correction view:
  - Simplest viable approach: shell out to open the file in the user's installed MuseScore 4 GUI for manual correction, and have the user re-save/export the corrected MusicXML back into the pipeline's working directory.
  - Stretch goal: render the score in-browser (e.g., via OpenSheetMusicDisplay) with inline editing, to avoid round-tripping through a separate desktop app.
- Block progression to Stage 3 until the user explicitly confirms "correction complete."
- Save the human-verified MusicXML as the canonical score for this sample — this is the file used for both audio synthesis and any measure/note-ID references in the label schema.

### Stage 3 — Reference Audio Synthesis (MuseScore CLI)

- Render the verified MusicXML to audio using MuseScore's CLI in converter mode:
  ```
  mscore -o reference.wav verified_score.musicxml
  ```
  or, for batch runs, a `-j job.json` batch file.
- Export to WAV, not MP3, to avoid lossy-compression artifacts before spectrogram/feature extraction.
- Pin a specific MuseScore version (4.2+ recommended; earlier 4.x builds have a known bug where CLI audio export produces silent files with Muse Sounds — fixed in 4.2, see https://github.com/musescore/MuseScore/issues/19160). Confirm the installed version at pipeline startup and warn if it's below 4.2.
- Run headless on Linux via `xvfb-run` since MuseScore's converter mode still requires a virtual display.
- Add a post-export sanity check: compute RMS/peak amplitude of the rendered audio and fail loudly if it's silent (protects against regressions of the above bug or misconfigured sound profiles).
- Allow configuring the soundfont/sound profile per instrument type (e.g., use a piano-appropriate soundfont for piano scores) via a config file, not hardcoded.

### Stage 4 — Performance Audio Input

- Accept a pre-recorded audio file (WAV/MP3/FLAC) from the user, or support in-app recording via the system microphone.
- Normalize sample rate/channels to match what Stage 6's feature extraction expects (e.g., resample to 22050 Hz mono, configurable).
- Store the raw performance audio alongside the pipeline outputs (not just its spectrogram) so it can be re-processed later if feature extraction parameters change.
- **Optional performer self-assessment capture**: if the performer is available at recording time (not just a separate expert annotator later), let them optionally mark rough timestamp ranges where *they* believe they made a mistake, before any expert review happens. Store these as a separate `self_reported` label list in the output (see schema below) — do not merge them into the expert `labels` list. This gives a third comparison point (self-perception vs. expert label vs. DTW-residual) at near-zero marginal cost.

### Stage 5 — Automatic Alignment & Candidate Error Detection

This stage runs after Stage 3 and Stage 4 are both available, and before the human annotator opens the Annotation UI.

- Extract chroma or CQT features (not raw mel spectrograms — these are timbre-sensitive and will confound alignment) from both the performance audio and the MuseScore reference audio.
- Run DTW (bounded warping window / Sakoe-Chiba band; prefer a jump-tolerant variant such as JumpDTW if the corpus is expected to include repeats, cuts, or grace notes/ornaments) to align the two sequences in time.
- From the alignment, derive **candidate error regions** automatically:
  - Local pitch-class mismatch at a given aligned time → candidate `wrong_pitch`
  - Local onset/offset deviation beyond a configurable tolerance (e.g., >100ms) → candidate `rhythm_error`, with the numeric ms-deviation stored
  - Cents-off-pitch beyond a configurable tolerance (e.g., >20 cents) → candidate `intonation_error`, with the numeric cents-deviation stored
  - Reference-side note with no aligned performance match → candidate `missed_note`
  - Performance-side note with no aligned reference match → candidate `extra_note`
  - Unusually steep or flat sections of the warping path → candidate structural discontinuity (flag for manual review, do not auto-classify)
- Store all thresholds (ms, cents, warping-slope bounds) in the same config file as Stage 3's soundfont settings — do not hardcode.
- Output a `candidates.json` (same shape as `labels.json`, see Stage 7 schema, but with `source: "auto"` and no `severity`/`comment` yet) to feed into Stage 6's UI as pre-highlighted regions.
- This stage is a detection aid, not ground truth — every candidate must still be confirmed, corrected, reclassified, or rejected by a human in Stage 6.

### Stage 6 — Annotation UI

Build a browser-based (or desktop) annotation interface with a **non-linear-editor-style timeline** as its core interaction model — modeled on the region/clip editing UX found in DaVinci Resolve, Premiere, or Audacity, since this is the most efficient known interaction pattern for selecting and labeling ranges on a time-based media track. This is the primary UI of the entire application and should be treated as such in implementation priority.

**Timeline component (core UX):**

- A horizontal, zoomable, scrollable timeline ruler showing elapsed time (mm:ss.ms), with the performance audio waveform rendered as the primary track beneath it, similar to an audio track in a DAW/NLE timeline.
- Zoom in/out controls (mouse scroll wheel + keyboard shortcuts, plus a zoom slider) so the user can work at a coarse level (seeing the whole piece) or a fine level (seeing individual note transients for precise boundary placement) — this is essential since some error boundaries need sub-100ms precision.
- Click-and-drag directly on the waveform to select a time range, the same way one selects a clip range on a timeline in DaVinci Resolve: click sets the start handle, drag sets the end handle, and the selected range is highlighted with a distinct fill color while dragging.
- Once a range is selected, both edge handles must remain independently draggable afterward, so the user can nudge the start or end boundary without re-selecting the whole range from scratch — mirroring how trim handles work on a timeline clip.
- Support keyboard-driven nudging of the selected range's boundaries (e.g., arrow keys move the nearest handle by one frame/a configurable small time step) for precision beyond what a mouse drag alone allows.
- A visible playhead that moves during playback and can be scrubbed by clicking/dragging along the ruler; pressing play should play from the current playhead position, and there should be a "loop selected range" toggle so the user can repeatedly listen to just the selected range while deciding on a label — critical for judging short, subtle errors.
- Support standard transport controls: play/pause, jump to start/end, step forward/backward by a small time increment, and adjustable playback speed (e.g., 0.5x/0.75x/1x) to help the user catch fast passages.
- Once a range is selected, labeling it should be a lightweight action: a hotkey or small popup/context menu lets the user assign a type from the taxonomy without leaving the timeline view (e.g., number-key shortcuts mapped to common label types, similar to marker-color hotkeys in video editors).
- After a range is labeled, render it as a colored, named block directly on the timeline (a second "labels track" beneath or overlaid on the waveform, akin to a marker/subtitle track in an NLE) so the user can see all existing labels at a glance, click one to edit/re-type/delete it, and visually spot gaps or overlaps.
- Support multiple stacked label tracks if needed (e.g., one track for error labels, one for repetition links, one for candidate/auto-detected regions from Stage 5) so overlapping information doesn't visually collide — this again mirrors multi-track layering in DaVinci Resolve's timeline.
- Pre-highlighted Stage 5 candidates (see below) should appear as their own visually distinct track/style (e.g., dashed outline, muted color) so they are clearly different from confirmed human labels until acted on.

**Score view alongside the timeline:**

- A rendered view of the score (e.g., via OpenSheetMusicDisplay rendering the verified MusicXML), displayed alongside or above the timeline, that scrolls/highlights in sync with the playhead so the user can visually follow the notation while listening — this remains a hard requirement alongside the timeline redesign, not a replacement for it.

**Candidate review workflow:**

- Load `candidates.json` from Stage 5 and render each candidate as a pre-populated block on the candidate track described above.
- The annotator's primary workflow is to click each candidate block and **confirm** (promotes it to a normal label, keeping its boundaries/type), **edit** (adjust its time boundaries via the same drag-handle interaction as any other range, or change its type), or **reject** it (removes it or converts it to a `stylistic_choice` non-error label) — plus create brand-new labeled ranges from scratch using the same click-and-drag timeline interaction for anything the automatic pass missed.

**Labeling taxonomy and metadata (attached to any selected range, whether newly drawn or promoted from a candidate):**

- Assign a `type` from a fixed, closed taxonomy:
  - `wrong_pitch` (a different pitch than the score specifies)
  - `missed_note` (a scored note was not played)
  - `extra_note` (a note was played that is not in the score)
  - `intonation_error` (pitch/tuning drift on an otherwise-correct note)
  - `rhythm_error` (timing/duration off)
  - `repetition` (performer re-attempting a previous phrase)
  - `stylistic_choice` (an explicit "not an error" tag — deliberate rubato, dynamics, or ornamentation that a naive alignment might flag but a human judges intentional; store these so they can be used as hard negatives during training rather than being silently skipped)
  - Allow an optional free-text `comment` field per label for edge cases, but keep the primary `type` field a closed enum for reproducible downstream processing.
  - The taxonomy list itself must live in the shared config file, not be hardcoded in the UI, so new categories can be added without a code change (see Deliverables).
- **Numeric deviation + severity**: for `intonation_error`, `rhythm_error`, `wrong_pitch` labels, auto-populate (and allow manual override of) the numeric deviation carried over from Stage 5's DTW residual (cents-off-pitch or ms-off-beat) when the label originated from a candidate. For manually-created labels with no residual available, allow the annotator to enter it directly if known, or leave null. Additionally let the annotator set a 1–5 severity slider on every error-type label (not just numeric-deviation-eligible ones), since severity is a useful graded signal beyond the raw physical deviation.
- **Repetition linking**: when a user labels a region as `repetition`, require them to also specify which earlier timestamp range it's a repeat of — ideally by letting them click the earlier range directly on the timeline to link it, rather than typing timestamps manually — and store this as a reference/pointer in the JSON, not just a flag, so the model can later learn "this segment restates that segment."
- **Score-position linking**: let the user optionally click a measure/note in the rendered score view to auto-associate the currently-selected timeline range with a `measure_number`/`note_id`, not just a raw timestamp. This makes labels useful even if performance tempo varies and gives a cross-check against Stage 5's alignment-based detection.
- Validate before allowing export: no overlapping labels of the same type on the same track without explicit confirmation, no zero-length regions, all `repetition` labels have a valid back-reference, every candidate from `candidates.json` has been either confirmed, edited, or explicitly rejected (none left in limbo).

**Suggested implementation approach:** build the timeline on a library purpose-built for this interaction pattern rather than from scratch — `wavesurfer.js` with its Regions plugin is a strong fit (it natively supports draggable/resizable labeled regions on a waveform, zoom, and playback sync) and can be extended with a custom multi-track overlay for the labels/candidates tracks described above. Evaluate it first before building custom canvas/SVG waveform-and-region rendering.

### Stage 6b — Inter-Annotator Review (sampling-based)

- Support assigning a sample to a second, independent annotator after the first pass is complete, without showing them the first annotator's labels.
- Provide a diff view comparing two independent label sets for the same sample: overlapping regions with matching types, overlapping regions with differing types/severity, and regions labeled by only one annotator.
- Track what fraction of samples have gone through double-annotation and store a simple agreement metric (e.g., IoU-based region overlap + label-type match rate) per reviewed sample in `metadata.json`, so label-quality/reliability can be reported later without re-deriving it from scratch.
- This does not need to run on every sample — support configuring a review sampling rate (e.g., review 10% of samples) rather than requiring it universally.

### Stage 7 — Feature Extraction

- Compute a log-mel spectrogram for both the performance audio and the MuseScore-rendered reference audio, using identical parameters for both (e.g., `librosa.feature.melspectrogram` with a fixed `n_fft`, `hop_length`, `n_mels`, sample rate — store these parameters in `metadata.json` so they're reproducible).
- Save each spectrogram as a `.npy` array (not just an image) to preserve numerical precision for model training.
- Also save a small PNG preview of each spectrogram for quick human sanity-checking.
- Persist the chroma/CQT features and DTW warping path computed in Stage 5 alongside the mel spectrograms (e.g., `alignment.npz`), so downstream model training or re-annotation doesn't need to recompute alignment from scratch.

### Stage 8 — Output Bundle

For each processed sample, write a self-contained directory:

```
sample_<id>/
├── verified_score.musicxml
├── performance_audio.wav
├── reference_audio.wav
├── performance_mel.npy
├── reference_mel.npy
├── performance_mel_preview.png
├── reference_mel_preview.png
├── alignment.npz          (chroma/CQT features + DTW warping path + per-frame residuals)
├── candidates.json        (Stage 5 auto-detected candidate errors, source="auto")
├── labels.json            (final human-confirmed labels, schema below)
└── metadata.json          (sample rate; mel + DTW params; MuseScore version/soundfont used;
                             OMR tool+version if applicable; schema_version; pipeline run timestamps;
                             annotator id(s); inter-annotator agreement score if reviewed)
```

`labels.json` schema (example):

```json
{
  "schema_version": "1.1",
  "audio_reference": "performance_audio.wav",
  "annotator_id": "annotator_01",
  "self_reported": [
    {"start_time": 2.0, "end_time": 4.8, "comment": "I think I went flat here"}
  ],
  "labels": [
    {
      "id": "lbl_001",
      "source": "auto_confirmed",
      "start_time": 2.3,
      "end_time": 4.5,
      "type": "intonation_error",
      "severity": 3,
      "deviation_cents": 34.2,
      "measure_number": 12,
      "note_id": null,
      "comment": "flat on the high C"
    },
    {
      "id": "lbl_002",
      "source": "manual",
      "start_time": 10.1,
      "end_time": 13.8,
      "type": "repetition",
      "repeats_label_range": {"start_time": 5.0, "end_time": 8.7},
      "comment": "restarted phrase after rhythm mistake"
    },
    {
      "id": "lbl_003",
      "source": "auto_rejected",
      "start_time": 20.0,
      "end_time": 21.2,
      "type": "stylistic_choice",
      "comment": "intentional rubato, not an error; auto-flagged by DTW but rejected on review"
    }
  ]
}
```

Notes on the schema:
- `source` distinguishes labels that originated from Stage 5's automatic detection (`auto_confirmed`, `auto_edited`, `auto_rejected`) from ones the annotator created from scratch (`manual`), so you can later measure how much the auto-detection pass actually helped.
- `self_reported` is kept separate from `labels` — it is performer self-perception, not ground truth, and should never be silently merged into the expert-reviewed label set.
- `deviation_cents` / `deviation_ms` fields are optional and only populated when a numeric residual is available (from Stage 5 or manual entry).
- `schema_version` must be bumped whenever the taxonomy or field set changes; see Deliverables for the required validation script.

### Stage 9 (Batch Mode) — Synthetic Error Injection

- Provide a script/mode that takes a verified MusicXML and programmatically generates corrupted variants by applying one or more of: shifting a note's pitch by N semitones or cents, delaying/advancing a note's onset by N ms, deleting a note, duplicating/inserting an extra note, or altering a note's duration.
- Re-render each corrupted variant through the same Stage 3 MuseScore pipeline to produce synthetic "performance" audio.
- Because the corruption is applied programmatically, the exact `labels.json` for each synthetic sample is known with certainty at generation time — no DTW alignment or human annotation needed for these samples. Generate it directly in the same schema as Stage 8's `labels.json`, with `source: "synthetic"`.
- Output synthetic samples in the same directory structure as real samples (Stage 8), so they can be mixed into the same training corpus or kept in a separate `synthetic/` root for clarity — make this configurable.
- This mode should be scriptable/headless (no UI dependency), since its entire purpose is to cheaply scale data volume using infrastructure already built for the real pipeline.

## Tech Stack Suggestions (adjust to your existing stack)

- Backend/pipeline orchestration: Python (subprocess calls to Audiveris and MuseScore CLI, `music21` for MusicXML parsing/validation/corruption in Stage 9, `librosa` for mel/chroma/CQT features, a DTW library such as `librosa.sequence.dtw` or a dedicated package supporting jump-tolerant variants)
- Frontend annotation UI: web app using `wavesurfer.js` for waveform/region selection + OpenSheetMusicDisplay for score rendering; or a desktop app (e.g., Electron/Tauri) if avoiding browser mic/file permission friction is a priority
- Storage: local filesystem per-sample directories as above; consider SQLite for an index/manifest across many samples once volume grows (this is also a natural place to store inter-annotator agreement scores and taxonomy version history)

## Non-Functional Requirements

- Every external tool invocation (Audiveris, MuseScore) must have its stdout/stderr captured and logged per-sample for debugging bad conversions later.
- Pipeline must be resumable: if a user closes the app mid-annotation, they should be able to reopen the same sample and continue rather than restarting from Stage 1.
- Config (soundfont paths, MuseScore binary path, Audiveris binary path, mel/chroma parameters, DTW thresholds, error-type taxonomy list, review sampling rate) should live in one config file, not be hardcoded across scripts.
- Include a `--batch` mode / scriptable entry point that skips the interactive annotation UI and only runs Stages 1–3, 5, and 7, for cases where you want to bulk-generate reference audio/candidates/spectrograms ahead of a separate annotation pass.
- Provide a standalone schema-validation script that checks any `labels.json` in the corpus against the current `schema_version`'s required fields and the current taxonomy enum, and run it in CI/pre-commit if the project has one, so a taxonomy change doesn't silently produce inconsistent old vs. new data.
