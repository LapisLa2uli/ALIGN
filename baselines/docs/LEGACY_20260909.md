# ALIGN baselines: Polytune and LadderSym

Everything needed to train and evaluate the two published error-detection baselines on ALIGN data.
Both models take a *performance* ("mistake") spectrogram and a *reference* ("score") spectrogram on the
same absolute timeline and transcribe the performance into three note classes: **Extra**, **Missed**,
**Correct**. LadderSym can additionally read the reference MIDI as a decoder prompt.

Everything below was set up and smoke-tested on a macOS arm64 machine without CUDA (all paths are
absolute and rooted at `/Users/tong172/Desktop/projects/ALIGN/baselines`, abbreviated `$B` here).
Real training has **not** been run; see section 6 for what is verified and what is not.

**Status (2026-09-09).** The source datasets (`synth-pipeline/output_10k_multi`, `output_2k_rawdata`) were
regenerated with the fixed generator (see `synth-pipeline/README.md`, "Fixes (2026-09-08)": transposition,
MIDI key signatures, label times, tie handling, `note_labels.json`). `data/align_v1` was built from them
(12000 tracks, 0 excluded by the consistency check: multi 9000/500/500, raw 1800/100/100 train/validation/test;
402k correct / 306k extra / 21.8k removed label notes) and `data/real_test` (73 recordings); both official
loaders and `check_labels.py` (60 tracks) pass on it. Training on this Mac was started on 2026-09-09 with
`scripts/mac_train_all.sh data/align_v1 3` (see "Mac profile" in section 3), sequentially:
`runs/laddersym/laddersym_prompted_align_v1_mac_<ts>`, then `runs/polytune/polytune_align_v1_mac_<ts>`, then
`runs/laddersym/laddersym_unprompted_align_v1_mac_<ts>`; progress in `runs/mac_train_all.log` and the
per-run `train.log` / `train_stdout.log`. Smoke tests (section 5) passed on cpu/mps; smoke checkpoints were deleted.

### Patches (why each one is needed)

Apply with `cd $B/Polytune && git apply ../patches/polytune.patch` (same for LadderSym). The patches only
touch tracked files; the new untracked config files (`config/config_align*.yaml`, `config/dataset/ALIGN.yaml`)
are already in place and are not part of the diffs. All changes keep the upstream behaviour when CUDA is
available unless marked **bug fix**.

Polytune (`inference_error.py`, `test_polytune.py`, `polytune_test_inference.py`):
- **Bug fix** in `InferenceHandler._split_token_into_length`: upstream pads the mistake/score *frames* to the
  longer of the two but not the frame-*time* arrays. Whenever the reference audio is shorter than the
  performance (every bundle with repeats, most real recordings) the trailing segments raised
  `ValueError: could not broadcast ...`, `inference()` swallowed it, no MIDI was written and the script
  still exited 0. Both time grids are now extended to the padded length (no-op for equal lengths).
- Device selection `cuda -> mps -> cpu` (`POLYTUNE_DEVICE` overrides) instead of hard-coded `cuda`;
  `.pt/.pth` weights load with `map_location="cpu"`; `eval.load_weights_strict` read with `.get()` (the key is
  absent upstream and raised).
- Output tracks are named `extra` / `missing` / `correct` via `instrument_infos` (upstream leaves them
  unnamed, so an absent class shifts the positions consumers rely on).
- `eval.max_length` (default null = upstream 1024) controls decoder tokens per 2.048 s segment (smoke tests only).

LadderSym (`inference_error.py`, `test_laddersym.py`, `laddersym_test_inference.py`, `tasks/laddersym_mt3_net.py`):
- Per-step debug prints (whole target tensor + two `.item()` syncs per batch) behind `LADDERSYM_DEBUG_PRINTS=1`;
  the zero-loss fallback tensor is created on the logits' device (was CPU, breaks backward on GPU).
- Device fallback `cuda -> mps -> cpu` (`LADDERSYM_DEVICE` overrides); `torch.compile` only with
  `LADDERSYM_COMPILE=1` (was unconditional); `map_location="cpu"` on checkpoint loads; `load_weights_strict` via `.get()`.
- Output tracks named `extra`/`missing`/`correct`; `LADDERSYM_DETERMINISTIC_PROMPT=1` stops the inference-time
  prompt shuffling (training never shuffles prompts, so this makes inference match training).
- `eval.max_length` as for Polytune.

## 2. Data: ALIGN bundles -> MAESTRO-E layout

### 2.1 Target layout (what both official loaders read)

```
<DATA_ROOT>/
  label/extra_notes/<id>/MIDI/<id>.mid      Extra   -> error_class 1 (token 1135)
  label/removed_notes/<id>/MIDI/<id>.mid    Missed  -> error_class 2 (token 1136)
  label/correct_notes/<id>/MIDI/<id>.mid    Correct -> error_class 3 (token 1137)
  mistake/<id>/mix.wav                      performance audio, 16 kHz mono PCM_16
  score/<id>/mix.wav                        reference audio, 16 kHz mono, zero-padded to the SAME length as the performance
  score/<id>/mix.mid                        reference MIDI (LadderSym prompt; required by the loader even when use_prompt=False and for Polytune)
  split.json                                {"midi_filename": {"0": "<set>/<id>.midi", ...}, "split": {"0": "train|validation|test", ...}}
  manifest.json                             per-track bookkeeping (bundle path, source, durations, class counts, split, padding)
```

Rules the loaders impose: label MIDIs exactly one directory below `<id>` (the loader keys on path component
`[-3]`), exactly one `.mid` per class per track, audio literally `mix.wav`, no other `mix.*` files, split
names exactly `train`/`validation`/`test`, all 5 files per track, a class with no notes still needs a valid
(empty) MIDI. Track ids may not contain `.mid`, `.wav`, `mix.`, `/` or spaces (the loaders do string
replacement on full paths); the converter rejects such ids and out-roots.

Segmenting: the models see 2.048 s of performance (256 frames at 125 fps = 16 kHz / hop 128) with a 4.096 s
score window centred on the same times. During training each piece is cut into 16 s chunks
(`split_frame_length=2000` frames) and `num_rows_per_batch` random 2.048 s segments are drawn per piece; **the
trailing partial chunk is dropped whenever at least one full chunk exists** (loader behaviour, not changed:
e.g. 12.8 s of a 60.8 s clip are never trained on).

### 2.2 Class semantics: our 6 span types vs. the models' 3 note classes

Converter mapping from `note_labels.json` (sounding pitch, performance timeline, `tie_prev` notes merged
into the preceding note, velocity 90, min duration 0.01 s, program 71):

```
correct = performance_notes[cls == "correct"]
extra   = performance_notes[cls == "extra"]     # sub wrong | inserted | repeat
removed = missed_notes[copy == 0]               # sub rest | wrong   (missed_notes with copy > 0 have no score counterpart and are ignored)
```

| ALIGN span label | what the models see | recoverable? |
|---|---|---|
| `wrong_note` | Extra (played pitch) + Missed (score pitch) with the same span | yes; `eval_bridge` re-pairs Missed+Extra within 0.1 s |
| `missed_note` | Missed (score note replaced by silence) | yes |
| `extra_note` | Extra (inserted note) | yes |
| `repetition` | every note of the repeated pass is Extra (`sub=repeat`); errors *inside* a repeated pass have no Missed counterpart | only heuristically (run of Extra notes matching preceding material); fragile |
| `rhythm_error` | the note is Correct (only its timing moved) | **no** (not expressible in Extra/Missed/Correct) |
| `intonation_error` | Correct (detuned by cents) | **no** (pitch is per semitone; mir_eval tolerance is 50 cents) |
| tempo-change errors | not a class; they shift the performance timeline relative to the reference | no; see section 6 |

In the 16 smoke bundles the Extra class is dominated by repeated-pass notes (846 of 877 Extra notes are
`sub=repeat`, 18 inserted, 13 wrong).

Bundles whose `note_labels.json` `check.perf.ok`/`check.ref.ok` is false (labels inconsistent with the exported
MIDI) are converted but **left out of `split.json`** unless `--keep-failed-check` is passed; the count is printed
and stored in `manifest.json` (`n_failed_check`, `excluded_failed_check`). None occurred in the smoke sets.

### 2.3 Running the conversion

`common/prepare_dataset.py` (run with the Polytune venv; needs only numpy/scipy/soundfile/pretty_midi):

```
prepare_dataset.py --out DATA_ROOT --set NAME=BUNDLE_ROOT [--set ...]
    [--val-frac 0.05] [--test-frac 0.05] [--seed 365] [--split-by-source [SET ...]]
    [--workers 2] [--limit K] [--real-test] [--overwrite] [--no-equalize-audio] [--keep-failed-check]
```

`scripts/prepare_data.sh` wraps the three datasets we use:

```bash
# tiny sets (already built from data/smoke_bundles): data/smoke_align (28 tracks, 14/7/7) and data/smoke_real (5 real recordings)
$B/scripts/prepare_data.sh smoke

# full sets: data/align_v1 (10k procedural + 2k real-score snippets, per-clip 90/5/5 split) and data/real_test
WORKERS=8 $B/scripts/prepare_data.sh full
#   = prepare_dataset.py --out $B/data/align_v1 \
#       --set multi=/Users/tong172/Desktop/projects/ALIGN/synth-pipeline/output_10k_multi \
#       --set raw=/Users/tong172/Desktop/projects/ALIGN/synth-pipeline/output_2k_rawdata \
#       --val-frac 0.05 --test-frac 0.05 --seed 365 --workers 8
#   + prepare_dataset.py --out $B/data/real_test --set real=/Users/tong172/Desktop/projects/ALIGN/data/test --real-test --workers 8
```

Extra args after the mode are forwarded (e.g. `--overwrite`). The converter is idempotent (existing outputs
are skipped; `split.json` is byte-identical across re-runs for the same inputs and seed). Outputs built with an
older converter that had unequal audio lengths are detected and rewritten automatically. After
*regenerating bundles* use `--overwrite`, because the skip path does not re-validate existing label MIDIs.

Real recordings (`--real-test`): `data/test` has `labels.json` only (no `note_labels.json`, no
`performance_audio.mid`), so the three label MIDIs are written empty and everything goes to `test`. Such a
DATA_ROOT is for the **inference/eval scripts only**: both official `Dataset` classes crash
(`IndexError` in `_extract_target_sequence_with_indices`) on a piece whose three label MIDIs are all empty,
so never point a train/val DataLoader at `data/smoke_real` or `data/real_test`. Note also that for real
recordings the reference audio/MIDI live on the *reference* timeline, not the performance timeline
(no alignment inside the models; inherent to the design).

### 2.4 Split policy and leakage caveat

- Per set, ids are shuffled with `random.Random(f"{seed}:{set}")` and split `round(frac*n)` with at least one
  clip per split when n >= 3.
- Both sets are split **per clip** (the default of `prepare_data.sh full`). The `raw` set is cut from only
  three scores (`001` demo scale, Mozart K.622, Weber), so random 8-16-measure snippets of the same score
  appear in every split with overlapping measures. This mirrors the practice setting (the same piece is
  practised repeatedly) but it is not a leakage-free split at the piece level.
- `--split-by-source raw` groups the `raw` set by `metadata.json["source"]` (the score stem) so that **all
  snippets of one score land in one split**. With only three sources the greedy assignment hands one whole
  score to test, one to validation and leaves one for training, which is why it is off by default; use it for
  a cross-piece generalisation experiment. It needs >= 3 distinct sources, otherwise it falls back to per-clip.
- The `multi` set has the single source `gen` (procedural generation) and is always split per clip.
- Whether the scores behind `data/test` (real recordings) overlap with the `raw` sources has not been checked.
  If they do, `raw` train clips of those scores are a (mild) form of leakage for the real test set.

## 3. Training (CUDA)

Configs: `Polytune/config/config_align.yaml` (+ `config/dataset/ALIGN.yaml`),
`LadderSym/config/config_align_prompted.yaml` (`use_prompt: True`, batch 2),
`LadderSym/config/config_align.yaml` (`use_prompt: False`, batch 4), each with `config/dataset/ALIGN.yaml`.
The dataset configs read `ALIGN_BASELINE_ROOT` and `ALIGN_BASELINE_SPLIT_JSON` from the environment; the
scripts export them. Defaults target one CUDA GPU: `trainer.accelerator gpu`, `precision bf16-mixed`,
`strategy auto`, `devices 1`, `num_workers 8`.

```bash
# Polytune (from scratch). --profile defaults to cuda; run dir = $B/runs/polytune/<run-name>
$B/scripts/polytune_train.sh --data $B/data/align_v1 --run-name polytune_align_v1 --profile cuda
#   options: [--split-json J] [--epochs N] [--batch-size N] [--resume <x.ckpt>] [--smoke] [--dry-run] [-- hydra overrides]

# LadderSym prompted / unprompted (from scratch). --profile auto = cuda if available
$B/scripts/laddersym_train.sh --data $B/data/align_v1 --prompted   --run-name laddersym_prompted_align_v1
$B/scripts/laddersym_train.sh --data $B/data/align_v1 --unprompted --run-name laddersym_unprompted_align_v1
#   options: [--split-json J] [--epochs N] [--warm-start <model.ckpt>] [--smoke] [-- hydra overrides]
#   (no --batch-size / --dry-run; use e.g. `dataloader.train.batch_size=4 dataloader.val.batch_size=4` as overrides)
```

Anything unrecognised (or after `--`) is passed through as a Hydra override. Both scripts set
`WANDB_MODE=offline` (wandb files stay in the run dir), `MPLBACKEND=Agg`, and tee stdout to
`<run>/train_stdout.log` (Polytune) / `<run>/train.log` (LadderSym). Checkpoints:

- Polytune: Lightning `.ckpt` under `<run>/polytune_ALIGN/<wandb-run-id>/checkpoints/` (`last.ckpt` +
  top-3 by `val_loss`), and a plain state dict `<run>/polytune_ALIGN/version_0/checkpoints/last.pt`
  written by `train_polytune.py` at the end.
- LadderSym: `<run>/laddersym_MT3Net_ALIGN/<wandb-run-id>/checkpoints/{last.ckpt, epoch=..ckpt, last.pt}`.
- Re-running with the same `--run-name` adds a new `<wandb-run-id>` directory next to the old one.
- Each Lightning `.ckpt` is ~2.1-2.3 GB; the `.pt` ~0.7 GB.

### Key hyperparameters (what they mean)

| key | default | meaning |
|---|---|---|
| `mel_length` | 256 | frames per input segment = 2.048 s at 125 fps (the model's receptive window; the score window is 2x that) |
| `split_frame_length` | 2000 | training chunk = 16 s; one random 2.048 s segment per chunk per row; trailing partial chunk dropped |
| `num_rows_per_batch` | 8 | 2.048 s segments sampled per piece per batch (upstream MAESTRO used 12 for multi-minute pieces; our clips are 15-115 s = 1-7 chunks) |
| `dataloader.train.batch_size` | Polytune 4; LadderSym 2 (prompted) / 4 (unprompted) | pieces per step; segments per step = batch_size x num_rows_per_batch |
| `optim.num_steps_per_epoch` | Polytune: ceil(n_train / batch_size), computed by `polytune_train.sh` from split.json (yaml placeholder 2500); LadderSym: computed inside `train_laddersym.py` | only feeds the cosine LR schedule (`num_training_steps = steps_per_epoch x num_epochs`) |
| `optim.warmup_steps` | 4000 | linear warm-up steps before the cosine decay |
| `optim.lr`, `optim.min_lr` | 2e-5, 1e-5 | AdamW peak LR and cosine floor |
| `optim.error_loss_weight` | 8 | multiplies the CE loss on the Extra/Missed error-class tokens (all other tokens weight 1) |
| `num_epochs` | 40 | `trainer.max_epochs` and the schedule length |
| `dataset_is_deterministic` | false | random segment start inside each chunk (true only for debugging) |
| `event_length` | 1024 | max target tokens per segment (LadderSym: prompt + target share the 1024 budget) |
| `modelcheckpoint` | every epoch, `save_top_k 3` on `val_loss`, `save_last` | |

If you call `train_polytune.py` directly (not through the script) pass
`optim.num_steps_per_epoch=<ceil(n_train/batch_size)>` yourself.

### Suggested defaults and expected cost

The yaml defaults (40 epochs, lr 2e-5, warmup 4000, batch 4 / 2, `num_rows_per_batch` 8, val + checkpoint every
epoch) were chosen for ~10-12k training clips of 15-115 s; they are **untested at scale** (only 1-epoch /
2-batch smoke runs were executed). With ~10.8k train pieces (90 % of 12k) they imply ~2.7k steps/epoch for
Polytune at batch 4 (~108k steps total) and ~5.4k steps/epoch for LadderSym prompted at batch 2 (~216k steps).
Wall-clock per epoch on CUDA: **unknown** (the only timing we have is CPU/MPS smoke steps of ~10-25 s per
batch, which says nothing about a GPU). Watch `val_loss` in the first epochs and cut `num_epochs` if it
plateaus. Multi-GPU (`devices>1`) is unverified.

### Mac (Apple Silicon / MPS) profile actually used here

`scripts/mac_train_all.sh [DATA_ROOT] [EPOCHS]` trains all three variants on this machine (default
`data/align_v1`, 3 epochs) **sequentially**: LadderSym-prompted, then Polytune, then LadderSym-unprompted.
(A first attempt ran Polytune and LadderSym concurrently at batch 4: the two processes exhausted the 32 GB
unified memory, swap went to 23 GB and steps became ~20x slower, so it was aborted.) It differs from the CUDA
defaults only in capacity/efficiency settings, not in the models:

| setting | CUDA default | Mac profile | why |
|---|---|---|---|
| `event_length` (target tokens / segment) | 1024 | **256** | ALIGN segments are monophonic: max 93 target tokens measured over 153 segments; decoder cost/memory drops ~4x |
| `prompt_length` (LadderSym prompt tokens) | 1024 | **384** | max 193 prompt tokens measured; the 1024+1024 prompted decoder OOMs on MPS at batch 2 x 4 rows |
| precision | bf16-mixed | 32-true | no MPS autocast in torch 2.3 |
| `dataloader.*.num_workers` | 8 | 0 | spawned workers were ~20x slower on macOS in a probe |
| batch x `num_rows_per_batch` | 4 x 8 / 2 x 8 | Polytune 2 x 4, LadderSym 2 x 2 | one model at a time fits MPS memory without swapping |
| `optim.warmup_steps` | 4000 | 1000 | schedule is ~8k steps (3 epochs x ~2.7k) instead of ~113k |

Measured step times on smoke data (batch 2, one model, no other load): Polytune ~7 s/step (8 segments),
LadderSym-prompted ~3 s/step (4 segments). With ~10.8k training pieces at batch 2 that is 5.4k steps/epoch,
i.e. on the order of 10 h per Polytune epoch and 4-5 h per LadderSym epoch on this Mac (estimates from the
probes, not measured over a full epoch). `eval.max_length` follows
`event_length`, so checkpoints from the Mac profile must be evaluated with `event_length=256`
(and LadderSym with `prompt_length=384`) passed as overrides to the eval scripts.

### First Mac results (2026-09-09, for calibration only)

LadderSym-prompted, 3 epochs on `data/align_v1` with the Mac profile (16.2k steps x 4 segments): val_loss
2.19 -> 1.94 -> 1.89. Evaluating `epoch=2-step=16200-val_loss=1.8932.ckpt` on 3 random test pieces
(`scripts/laddersym_eval.sh ... --profile cpu --first-n 3 -- event_length=256 prompt_length=384`) gave
note-level micro F1 0.02 (correct 0.05, extra 0.0, missing 0.0) and span-level F1 close to 0; the decoder
emitted mostly invalid event streams (156 "note-off for inactive pitch" decode errors over 3 pieces).
Teacher-forced diagnosis on validation segments: 57 % token accuracy overall, 31 % on the error-class
tokens, and the `shift` (timing) tokens are essentially not learned yet -- i.e. the model is undertrained,
not mis-wired. For scale: the upstream MAESTRO-E schedule is ~5.4 M segment-samples (350 epochs x 323 steps
x 48 segments); this run saw ~65 k (about 1 %). Treat the Mac runs as an end-to-end pipeline check and
run the 40-epoch CUDA schedule for reportable numbers.

### Warm-starting from the official checkpoints (optional)

- **LadderSym**: official MAESTRO-E checkpoints are on Hugging Face
  (`ben2002chou/laddersym-checkpoints`, `checkpoints/maestro/{prompted,unprompted}/model.ckpt`). Download with
  `cd $B/LadderSym && ../envs/laddersym/bin/python setup_laddersym_assets.py --datasets none --checkpoints prompted`
  (-> `pretrained/laddersym/checkpoints/maestro/prompted/model.ckpt`), then
  `laddersym_train.sh --warm-start <model.ckpt> ...`, which sets `path=<ckpt> use_lightweight_checkpoint=True`:
  the weights are loaded with `strict=False` and training starts fresh (new optimizer/schedule/epoch counter).
  Side effect: `train_laddersym.py` writes `<ckpt>_lightweight.ckpt` next to the source checkpoint.
  Not exercised here (no download was made).
- **Polytune**: official checkpoints at `https://huggingface.co/ben2002chou/Polytune/tree/main/MAESTRO-E`.
  Warm-starting is **not wired**: `train_polytune.py` treats `path=<x>.ckpt` as a full Lightning *resume*
  (trainer state incl. epoch counter and optimizer) and `path=<x>.pth` as MAE *encoder* weights. Loading only the
  weights from the official `.ckpt` would need a small addition to `train_polytune.py`. `polytune_train.sh --resume`
  is meant for our own `.ckpt` files.
- Piano-trained weights on clarinet audio: no evidence either way about whether they help.

## 4. Evaluation

### 4.1 Official protocol (`test_polytune.py` / `test_laddersym.py` + `evaluate_errors.py`)

```bash
$B/scripts/polytune_eval.sh  --ckpt <last.pt|x.ckpt> --data $B/data/align_v1 --tag polytune_v1 [--split test] [--profile auto|cuda|mps|cpu] [--first-n K] [--batch-size N] [--bundles <bundle root>]... [--dry-run]
$B/scripts/laddersym_eval.sh --ckpt <last.pt|x.ckpt> --data $B/data/align_v1 --prompted|--unprompted --tag laddersym_v1 [--split test] [--profile ...] [--first-n K] [--bundles ...]... [--randomize-prompt]
```

- The official scripts enumerate the `test` split of `split.json`, run `InferenceHandler` on the whole
  performance (all 2.048 s segments, greedy decoding, `max_length` 1024 new tokens per segment, no KV cache),
  and write **one MIDI per piece** at `<hydra_run_dir>/<tag>/<track_id>/mix.mid`, i.e.
  `$B/runs/polytune/eval_<tag>/<tag>/<id>/mix.mid` and `$B/runs/laddersym/eval_<tag>/<tag>/<id>/mix.mid`.
  Tracks are Extra, Missing, Correct in that order (`note.instrument` 1/2/3), now also *named*
  `extra`/`missing`/`correct` by our patch. Upstream, an absent class is simply not written, which shifts
  the positions.
- `evaluate_errors.py` then prints per-piece `Onset F1` (all classes pooled) and `Track 0/1/2 F1`
  (Extra/Missing/Correct, positional zip over `pretty_midi` instruments) using
  `mir_eval.transcription.precision_recall_f1_overlap(onset_tolerance=0.05, offset_ratio=None)` (onset +
  pitch, offsets ignored) and averages per piece (a piece with an empty side scores 0). Pieces without a
  prediction are skipped with `[WARN] ... ground-truth items without estimates`.
- Both test scripts hard-code `split="test"`; `--split validation|train` works by writing a derived split file
  in the run dir that relabels the chosen split as `test`.
- `--first-n K` maps to upstream `eval.eval_first_n_examples`, which takes a **random, unseeded window** of K
  pieces (not the first K) -- two runs evaluate different pieces.
- `--max-length N` (both eval scripts, `laddersym_infer.sh`, `polytune_infer.sh`) is for smoke tests only;
  leave it unset for real numbers.
- `.pt`/`.pth` state dicts and Lightning `.ckpt` files are both accepted by the eval scripts;
  `laddersym_infer.sh` (wrapping `laddersym_test_inference.py`) accepts `.ckpt` only.
- Both scripts exit non-zero if no prediction was written (upstream swallows inference exceptions and exits 0;
  look for `Traceback` in `eval_stdout.log` / `eval.log`).

### 4.2 Our evaluation bridge (`common/eval_bridge.py`)

Both eval scripts call it automatically after the official evaluation when `$B/common/eval_bridge.py` exists:
`eval_bridge.py --pred-dir <run>/<tag> --bundles <bundle root>... [--ids-from <split json> --split test] --out <run>/eval_bridge.json`.
Bundle roots come from `--bundles` (repeatable) or, by default, from the distinct parents of the `bundle`
paths in `<DATA_ROOT>/manifest.json`. `--ids-from` is only passed when no `--first-n` subset was evaluated
(otherwise every un-predicted piece would count as an empty prediction). `polytune_eval.sh` accepts
`EVAL_BRIDGE_ARGS` / `EVAL_BRIDGE_PYTHON` to override the call; `laddersym_eval.sh` does not, so re-run the bridge
by hand for non-default flags. It runs in any of the three venvs (polytune, laddersym, project `.venv`).

```bash
$B/envs/polytune/bin/python $B/common/eval_bridge.py --pred-dir $B/runs/polytune/eval_<tag>/<tag> \
    --bundles /Users/tong172/Desktop/projects/ALIGN/synth-pipeline/output_10k_multi \
    --bundles /Users/tong172/Desktop/projects/ALIGN/synth-pipeline/output_2k_rawdata \
    --ids-from $B/data/align_v1/split.json --split test --out results.json \
    [--gold-first-pass-only] [--rep-gap-mode rest --rep-gap 2.0] [--pitch-mode hz|raw-midi] [--class-source auto|name|order] [--verbose]
```

**A. Note level** (the papers' protocol). Ground truth comes from `note_labels.json` with the same class
mapping as the converter. Per class (`extra`, `missing`, `correct`) and pooled (`all`): `mir_eval`
onset-50 ms / pitch F1, reported as micro (pooled TP/pred/GT over pieces), mean of per-piece F1 (mir_eval
convention, what the official script averages), mean over pieces with GT > 0, plus an `official_replica` block
that reproduces the official positional zip (verified identical to `mt3_program_aware_note_scores` on 32
piece comparisons). Use micro or `meanF1(gt>0)` as headline numbers: `missing` has many pieces with zero GT
notes, which score 0 under the per-piece mean (93.8 for a perfect oracle on the smoke set).

Pitch tolerance vs the official script: the task brief suspected `evaluate_errors.py` compares raw MIDI numbers
as if they were Hz (which would accept +-1 semitone). We read `note_seq.sequences_lib.sequence_to_valued_intervals`
in both pinned envs (note-seq 0.0.3 and 0.0.5): it converts to Hz, so the **installed official script compares in
Hz with a 50-cent tolerance**, as does the bridge by default (`--pitch-mode hz`; `--official-pitch-mode` selects the
same). `--pitch-mode raw-midi` reproduces the lenient variant if needed for comparison with published numbers.
Class assignment uses the track names our patches write; unnamed decoder output falls back to positional
order with a warning whenever the track count is not 3 (`n_ambiguous_track_order` in the JSON).

**B. Span level** (our task). Predicted notes are mapped to spans and scored with the errdet protocol (greedy
1-1 onset matching at 50/100/200 ms; the functions are vendored from `errdet/metrics.py` and verified identical
on random inputs): mutual-nearest Missed+Extra pairs within `--tau-wrong 0.1` -> `wrong_note`; remaining Missed ->
`missed_note`; runs of >= 3 consecutive Extra notes whose pitch sequence repeats the preceding material (LCS >= 0.8)
-> `repetition`; remaining Extra -> `extra_note`; `rhythm_error` / `intonation_error` are never predicted (rows kept
so recall 0 is visible). GT defaults to all `labels.json` spans (first + repeated passes, like errdet);
`--gold-first-pass-only` keeps first-pass labels only. Bundles without `note_labels.json` (real recordings) get
part B only.

Oracle results on the 16 smoke bundles (ground truth fed back as predictions): note level 100 % everywhere; span
level with `--gold-first-pass-only`: `wrong_note` 100, `missed_note` 100, but `extra_note` 15 / `repetition` 33 with
the specified default gap (0.35 s inter-onset), 68 / 71 with the recommended `--rep-gap-mode rest --rep-gap 2.0`
(90 / 69 adding `--rep-window-min 20`). With all labels as gold, `wrong_note`/`missed_note` recall is capped at
~43-46 % even for the oracle, because errors inside repeated passes have no Missed counterpart. Under noise
(5 random Extra + 5 random Correct notes per piece) `repetition` F1 drops from 71 to 15, so **treat span-level
`repetition`/`extra_note` numbers as indicative only; note level is the reliable headline.** Decide the gold mode and
the `--rep-*` flags before producing tables (defaults were left as specified).

## 6. Known limitations and TODOs

Model / protocol limitations (inherent to Polytune and LadderSym, copied as-is):
- **No alignment between performance and reference.** The score window is taken at the same absolute time as
  the performance segment. Repeats, tempo-change errors, hesitations and any real-recording timing drift
  shift the performance relative to the reference, so the model sees increasingly unrelated score context.
  For real recordings the reference is on its own timeline altogether. Our converter zero-pads the shorter
  audio so both loaders enumerate the full performance, but it cannot fix the misalignment.
- **Intonation and rhythm errors are undetectable** (section 2.2); repetition is only reconstructable
  heuristically and fragile under noise.
- **Trailing partial 16 s chunk is dropped** during training when a full chunk exists (a converter option to pad
  to the next 16 s boundary was considered but not implemented because it changes segment statistics).
- **Loader crash on all-empty label MIDIs**: `Dataset.__getitem__` raises `IndexError` on a piece whose three
  label MIDIs are all empty. Real-test DATA_ROOTs are for the inference scripts only.
- **Inference is slow**: greedy decoding without KV cache, up to 1024 tokens per 2.048 s segment; LadderSym
  prompted re-encodes the padded 1024-token prompt at every step.
- `--first-n K` evaluates a random, unseeded window of K pieces.
- `pretty_midi` drops note-less instruments on reload, so an empty class file re-reads as 0 instruments;
  note_seq / mir_eval accept it, but code asserting `len(instruments) == 1` will trip.
- Official per-piece averaging scores a piece with an empty side as 0 (both official script and bridge
  `per_piece_mean`).

Data limitations:
- The real test set (`data/test`, 73 recordings) has span labels only: no note-level ground truth, so only the
  span-level bridge (part B) applies; its repetition labels are single re-attacked notes, which the
  >= 3-note rule can never detect, and it has no `missed_note` labels at all.
- Repetition GT spans start at the measure boundary, which can precede the first repeated note by up to
  ~0.5 s (counts as FP+FN at 50 ms even for a correct detection); 1-2-note repeated measures are below
  `--rep-min-run 3`.
- Timeline: label MIDIs are quantised to 480 ticks/quarter at 120 bpm (~1 ms); the official evaluator's own
  combined-reference rewrite uses 220 ticks/quarter (~2.3 ms), which can differ from the bridge for onsets
  within a few ms of the 50 ms boundary.
